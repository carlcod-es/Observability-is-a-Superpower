# Architecture

How the demo application is built: the solution, the local environment, the site, the booking service,
the telemetry and the agent's access to it. Run instructions are in `README.md`. Diagrams:
`docs/media/architecture.svg` (system) and `docs/media/telemetry.svg` (telemetry flow).

## Overview

A fictional marketing agency site, **Rubber Duck Agency** (code names use `Acme`), built on Umbraco and
run with .NET Aspire. Visitors browse pages and submit three forms. A small booking service counts event
bookings behind a message queue. Logs, traces and metrics leave every service through OpenTelemetry and
reach two places: the Aspire dashboard (the developer's view) and Grafana LGTM (playing the production
observability platform). A coding agent (Claude Code) reads Grafana over MCP, read-only.

Platform: .NET 10, Umbraco 17 LTS, .NET Aspire 17, OpenTelemetry. Package versions are pinned centrally in
`Directory.Packages.props` (exact versions only).

## Local environment (AppHost)

One command starts everything: `aspire start --apphost src/SuperPower.AppHost/SuperPower.AppHost.csproj`.

| Resource | What it is | Ports | Persistence |
|---|---|---|---|
| `site` | `SuperPower.Web` project | 44368 (https), 21258 (http) | - |
| `api` | `SuperPower.Api` project | 5290, no external endpoint | - |
| `sql` / `umbraco` | SQL Server container (`AddAzureSqlServer(...).RunAsContainer()`) | dynamic | persistent container `oisp-sql`, volume `oisp-sql-data` |
| `smtp4dev` | mail catcher `rnwood/smtp4dev` | 2525 SMTP, web inbox | in memory |
| `cache` | Redis | dynamic | persistent container `oisp-cache`, volume `oisp-cache-data` |
| `queue` | RabbitMQ with management UI | dynamic | persistent container `oisp-queue`, no volume |
| `collector` | OpenTelemetry Collector contrib | dynamic | - |
| `lgtm` | `grafana/otel-lgtm`: Grafana, Loki, Tempo, Prometheus | 3000 (Grafana) | none: telemetry is lost on restart |
| `grafana-mcp` | `grafana/mcp-grafana`, read-only | 8091 (`/mcp`) | - |

Start order: `lgtm` first; `collector` and `grafana-mcp` wait for it; `site` waits for `sql`, `smtp4dev`
and `collector`; `api` waits for `cache`, `queue` and `collector`. `site` references `api` and `queue` but
does not wait for them: it must run without them. A generated secret parameter,
`telemetry-redaction-key`, is passed to `site` and `api` for log pseudonymisation.

### Two ways to run the site

| | Full environment (AppHost) | Standalone |
|---|---|---|
| Command | `aspire start ...` | `dotnet run --project src/SuperPower.Web` |
| Database | SQL Server container | SQLite file `umbraco/Data/Umbraco.sqlite.db` |
| Mail | smtp4dev | none |
| Telemetry | OTLP to the collector | none exported |
| Booking service | yes | no (no count, nothing queued) |

The AppHost configures the site through environment variables (connection strings, SMTP, owner address,
OTLP endpoint), so the same code runs in both modes. The two databases are independent; each is filled from
uSync on its first start.

## The site (`src/SuperPower.Web`)

**Pages:** Home, About us, Contact us, Events (list and event pages), Services (list and service pages).
Content, document types, templates and media are committed as uSync files (`uSync/v17/`) and imported
on the first start of an empty database (`ImportOnFirstBoot`). Models are generated by ModelsBuilder and
committed (`Models/`). Styles and script are `wwwroot/css/site.css` and `wwwroot/js/site.js`; fonts are
self-hosted and pages load no external resources. The layout works from phone to desktop, with a
collapsible main navigation.

**Events:** one document type with title, description and start date and time (with time zone). Free; no
capacity. On import, start dates are shifted by the whole days between a fixed reference day and the import
day (local time kept), so a fresh database always has one past event and the rest upcoming within four
weeks. The committed files keep the original dates. A past event shows "This event has ended" and no form.
Past/upcoming rules run on `TimeProvider` (`Events/`).

**Forms** (`Forms/`): three forms fixed in code; the page type decides which form a page shows.

| Page | Form | Fields |
|---|---|---|
| Contact us | Contact | Name, Email, Message |
| Service page | Service enquiry | Name, Email, Company (optional), Website (optional), Message |
| Upcoming event page | Event booking | Name, Email, Notes (optional), Join mailing list |

- One partial view per form (`Views/Partials/Forms/`), posted to `AcmeFormsController` (a
  SurfaceController) with antiforgery. Validation is server-side only; no format rule beyond Email.
- **Storage:** one site-owned table, `acmeFormSubmission`: form key, page key, UTC timestamp, reference
  number, field values as JSON. Created by the site's migration plan on start. No IP or browser data. Data
  access uses NPoco `Sql<ISqlContext>` builders (no raw SQL) so it works on SQLite and SQL Server.
- **Reference:** each stored submission gets the next number, shown as `ACME-nnnn` (unique index). The
  visitor sees "Thank you, we'll be in touch. Your reference is ACME-nnnn." and the form is hidden.
- **Owner notification:** every stored submission sends one email through Umbraco's `IEmailSender` to the
  owner address (`Acme:Forms:OwnerEmail`; smtp4dev locally), subject `New <form> submission ACME-nnnn`,
  fixed text. Submitters get no email. A submission that fails to store sends no email.
- **Event booking:** after storing, the site publishes a message to the booking service (below).

## Booking service (`src/SuperPower.Api`)

A minimal API that owns the booking count for each event.

1. **Publish (site):** after an event booking is stored, `RabbitBookingEvents` puts
   `{"eventKey":"<event page GUID>"}` on the durable queue `booking-stored`. No personal data.
2. **Consume (api):** `BookingStoredConsumer` (a background service) reads each message, increments the
   Redis key `event:<eventKey>:bookings`, adds 1 to `acme.bookings.counted` and acks. If processing fails it
   records the error and drops the message (nack, no requeue).
3. **Read (site):** an event page calls `GET /events/{eventKey}/bookings` on `api` and shows
   "n people have booked this event" (nothing at 0).

**Fail-soft:** the site works without `api`, `queue` or `cache`. The count read is capped at 2 s and
the page renders without it; publishing is capped at 2 s, never throws and logs a warning on failure. A
visitor always gets the confirmation, so a problem downstream is visible only in telemetry. Without a
`queue` connection string (standalone) publishing is a no-op.

## Telemetry

Set up once in ServiceDefaults (`AddServiceDefaults()`), used by `site` and `api`. Application code does
not depend on the exporter.

**Exporters:** `APPLICATIONINSIGHTS_CONNECTION_STRING` set: Azure Monitor. Otherwise
`OTEL_EXPORTER_OTLP_ENDPOINT` (set by Aspire): OTLP to the collector. Otherwise nothing.

**Collector:** two pipeline sets per signal: `*/aspire` to the Aspire dashboard and `*/lgtm` to Grafana
LGTM. The LGTM exporter has retries and its queue off: if `lgtm` is unreachable, batches are dropped.

**Traces:** ASP.NET Core, HttpClient and SqlClient instrumentation (SQL spans only under a recorded
parent, which drops Umbraco's background queries), Redis and RabbitMQ client spans, plus:
- `Acme.Forms` ActivitySource (site): `acme.forms.submit` per form post (`acme.form`,
  `acme.form.outcome` = stored / invalid / failed, `acme.submission.reference`), child `acme.forms.notify`
  (email) and `acme.forms.publish` (booking queued).
- `api` server and consumer spans tagged `acme.event.key` (event GUID only). One trace runs
  site -> queue -> api -> cache.

**Metrics:** ASP.NET Core, HttpClient and .NET runtime, plus:
- `acme.forms.submissions` (Meter `Acme.Forms`) by `acme.form` and `acme.form.outcome`.
- `acme.bookings.counted` (Meter `Acme.Bookings`), no attributes, recorded at 0 on start.
- `http.server.request.duration` and the request span tagged `acme.page_type`: the rendered content type
  (`home`, `page`, `contact`, `events`, `event`, `services`, `service`) or `none`. A small fixed label set:
  no URLs or query strings in metrics.
- Counters are cumulative and reset when a service restarts: query with `increase` or `rate`.

**Logs:** Umbraco logs through Serilog; a sink in ServiceDefaults forwards Serilog events to the
OpenTelemetry logger, so they keep named properties and link to their trace. No console sink: logs leave
the services only through OpenTelemetry (Umbraco also writes its own files under `umbraco/Logs/`). Log
levels are set in the site's Serilog configuration. Application logs:
- site: `Form {Form} for {Page} stored as {Reference}` (`Page` = page name).
- api: `Booking recorded for {EventKey}, count {Count}`; on failure an error log
  `Booking update failed for {EventKey}` with the exception.

**Filtered out:** `/health`, `/alive`, `/umbraco/backoffice`, `/css`, `/js`, `/media`, `/assets`,
`/favicon.ico` leave no spans or request logs (`TelemetryPaths.cs`); the request metric counts them as
`acme_page_type="none"`.

### Personal data

Never recorded: Name, Email, Message, Notes, Company, Website. Fine to record: form, page (event or service
title), outcome, reference. The rule for code: log what happened (form, outcome, reference), never the
submitted model or field values.

`PersonalDataLogProcessor` (ServiceDefaults) is a safety net, the first processor on the OpenTelemetry
logger, so it rewrites every log entry before any exporter sees it:
- attributes named Name, Email, Message, Notes, Company or Website (last name segment) become `[REDACTED]`;
- every email address becomes `[REDACTED:<id>]`, where id is the first 12 hex characters of an HMAC-SHA256
  of the lower-cased address, keyed by `Telemetry:RedactionKey`. The same address gives the same id, so
  repeat submitters can be counted without being named.

It does not cover traces, metrics or exception messages; code must not put personal data there. The agent
has no database access, so stored submissions are never visible to it.

## Dashboards and demo traffic

Grafana provisions `src/SuperPower.AppHost/grafana/dashboards/*.json` into folder "Demo" on every `lgtm`
start; UI edits are not saved.
- **Demo site:** Request rate by page type, Error rate (5xx), Request duration p95 by page type (with
  trace exemplars), Error logs (site), Form submissions by outcome, Bookings: stored vs counted.
- **ASP.NET Core:** community dashboard 19924.

Traffic tools (file-based C# apps):
- `tests/traffic/traffic.cs`: steady GET traffic, about one page per second.
- `tests/traffic/burst.cs`: concurrent valid form posts with made-up data, round-robin over the forms.
- `tests/load/burst.cs` and `tests/load/load-test.mjs`: stage burst and GET load test.

## Agent access (Claude Code)

- `.mcp.json` registers only `grafana` (`http://localhost:8091/mcp`): the Grafana MCP with writes disabled
  and only the Loki, Tempo, Prometheus and datasource tools enabled. All its tools are pre-approved in
  `.claude/settings.json`.
- The Aspire MCP (`aspire agent mcp`) is opt-in (README). Its read tools are pre-approved; resource
  commands prompt on every call.
- The agent never restarts services: after a code change it asks, and a person uses Rebuild on the
  resource in the Aspire dashboard (Restart does not recompile).
- No database, cache or queue access for the agent.

## Data and resets

| Data | Where | Reset |
|---|---|---|
| SQL Server database | volume `oisp-sql-data` | stop the AppHost, remove container `oisp-sql` and the volume |
| SQLite database | `src/SuperPower.Web/umbraco/Data/Umbraco.sqlite.db` | delete `Umbraco.sqlite.db*` |
| Umbraco caches and indexes | `src/SuperPower.Web/umbraco/Data/TEMP/` | delete with either database reset |
| Booking counts | volume `oisp-cache-data` | remove container `oisp-cache` and the volume |
| Queued messages | container `oisp-queue` | remove the container with `-v` |
| Telemetry, emails | `lgtm`, `smtp4dev` | restart the AppHost |
| Content and media | `uSync/v17/`, `wwwroot/media/` (committed) | source of truth |

Every clone shares the persistent containers and volumes (fixed names). After a database reset, uSync
imports the content again and the events get fresh dates.

## Tests

- `dotnet test SuperPower.slnx`: unit tests for form validation, field-to-JSON mapping, past/upcoming
  rules and event date shifting (fake `TimeProvider`), page-type values, reference format, notification
  text, booking count client.
- `dotnet run tests/smoke/smoke.cs`: end-to-end check on a freshly started AppHost (pages, forms, stored
  rows, emails, traces, metrics, dashboards, booking count). `-- running` for an environment already in
  use; `-- standalone` for the SQLite run.
